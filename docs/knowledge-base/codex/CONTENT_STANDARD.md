# 笔记写作与审阅标准

## 读者应当得到什么

每篇解决一个主要问题。开头明确学习成果和必要先修，然后从具体情境引出原理。读者不仅知道定义，还能运行例子、解释失败、选择方案、完成一个改变条件的练习。

默认中文，术语首次出现补英文。标题适度用问题句，但不追求所有标题整齐。短段落、少量必要表格、可复制代码、恰当留白；不用术语堆叠制造“专业感”。普通概念约 1,000–2,500 中文字作为编辑参考，不是强制最低字数；复杂主题拆系列。

## 六种正文类型

| 类型 | 必须回答 | 不应做 |
| --- | --- | --- |
| concept | 是什么、为什么、如何运作、边界/反例 | 只有定义或类比 |
| tutorial | 前提、文件、命令、步骤、结果、失败排查 | 步骤不能运行或省略依赖 |
| how-to | 症状、适用条件、诊断、修复、验证、回退 | 无背景直接给危险命令 |
| reference | 速查入口、语义、最小示例、指向解释 | 复制整本概念正文 |
| case-study | 约束、方案、选择、证据、版本、代价 | 虚构用户项目实现/指标 |
| lab | 假设、变量、环境、操作、观测、解释、清理 | 把预期写成实测、把本机扩展为生产保证 |

导航类用于路线与索引，不能计入“已完成教学文章”数量。

## 推荐正文结构

摘要/读完能做什么 → 场景 → 直觉 → 准确机制 → 最小例子 → 失败例子 → 适用/不适用 → 练习与提示 → 总结 → 来源和下一步。不同类型可调整顺序，不能机械保留空章节。

类比必须落回机制，例如讲队列后说明确认、重复投递和积压，不拿排队故事替代系统语义。存在简化时明确列出省略内容。不要为了入门写出不正确的绝对结论。

## 示例规范

给出目录、依赖/版本、运行命令、输入、预期输出及与实际核验的关系。完整例子在 examples/ 下，文章只摘与当前问题相关部分并链接源码。不要把有状态截断代码称为“复制即可运行”。

每个关键例子至少有正常路径和失败/边界路径。数值、时间、随机行为尽量控制，不能控制则说明允许范围。不使用真实账户、token、生产数据库或个人信息。命令可能覆盖数据时给安全范围，默认隔离测试数据。

自动运行只执行受维护的示例脚本或 manifest 中明确允许的测试，不从任意 Markdown 代码块提取并执行 shell。防止文档内容变成执行入口。

## 练习与掌握

练习改变至少一个条件：字段、限制、并发、错误输入、故障顺序或数据规模。读者需预测、解释、修复或比较，而不是只抄定义。提示和参考答案与题目分开；关键前提/安全注意事项不能藏在折叠区域。

文章 reviewed 只表示编辑与核验完成，不表示用户学会。个人自测结果、习惯、学习进度不写入公开仓库。静态路线完成标记若涉及个人状态，暂不实现在线同步。

## 引用与真实性

优先官方文档、标准、原始论文和对应项目源码。技术语义、版本行为、重要数字和保证在相关段落旁标来源，末尾列参考。内容改写和原创例子，不整段搬运教材。图像必须可用且有来源/许可记录，优先原创可维护图。

版本敏感的命令/API在编写时在线核对。verified_on 仅填实际核验日期，不自动设今天；tested_with 填实际运行环境。来源打不开或不能运行时写明影响，保留 draft；对不受影响的其他内容可以继续。

示例测试通过不等于全部事实正确；自审不冒充独立专家评审。可用第二次独立阅读或独立上下文作编辑复核，但避免同一文件并行写入。

## 反幻觉检查

检查“总是/绝不/100%/exactly-once/无锁/线性一致/持久化”等强断言的条件；区别协议保证与应用保证。性能结论必须记录机器、版本、数据、负载、方法与结果，不虚构百万 QPS、零丢失或未实测收益。

## 发布前读者视角检查

是否知道从哪里开始？先修是否真实存在？例子是否能运行？一处反例是否解释充分？下一步是否有效？手机上代码能否阅读？主要结论能否由证据支持？任何一项不满足，修复后再设 reviewed/publish。
