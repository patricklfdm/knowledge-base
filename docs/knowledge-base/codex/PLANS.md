# 可恢复执行计划约定

参考 OpenAI 的 ExecPlans 思路，但以下是本项目自行维护的轻量格式，不要求安装额外工具或开启某个自动运行功能。

跨多个文件、涉及 UI/示例/CI 或超过一次简单编辑的任务，先在 `docs/knowledge-base/codex/plans/` 写 `Hn-任务ID-短名.md`。一个简单拼写修复可直接记录报告，不为流程堆文件。

## 每个计划必须自包含

1. 目标与用户可见收益：完成后读者能做什么。
2. 当前事实：入口文件、命令、版本、相关基线；说明未知。
3. 范围与非目标：防止重做平台或延伸其他项目。
4. 具体步骤：小批实现、路径、必要依赖。
5. 验证：命令、预期断言、失败 fixtures、人工阅读检查。
6. Progress：未做/进行/完成，随工作更新。
7. Decisions and discoveries：选择和实际发现，附原因。
8. Recovery：中断后下一动作；临时资源清理；不得碰用户资料。
9. Outcome：实际结果、证据、遗留问题及本地/线上发布状态。

## 落地要求

计划必须能让不知道原聊天的 Codex 从仓库状态继续。不是写完一份长计划就算实现。每完成一个有意义步骤更新 Progress；新发现推翻假设时修计划，不硬照过期方案跑。

基线错误不改写成成功；测试命令还未实现时标计划，不在报告中当已执行。代码和内容状态与计划一致。

## 第一份计划

建议 `plans/H0-001-takeover.md`，范围严格按照 FIRST_TASK。H0 通过后就写 H1 的最小检查计划，避免在架构讨论阶段停住。
