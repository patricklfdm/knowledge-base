# 内容复核与维护

H7-002维护入口。读者使用[反馈说明](../../content/maintenance.md)与GitHub表单；维护者使用本流程。任务状态只在[codex/BACKLOG.json](codex/BACKLOG.json)，本文与观测文件不另设任务台账。

## 什么时候复核

每个内容批次开始运行 `npm run kb:review`；固定运行时或依赖改动、发现来源异常、读者提交问题时增加专项复核。已核验教学文默认180日进入提醒，等于180日也计入。这个间隔是本项目维护策略，不是内容有效期，不会自动撤下或刷新日期。目前没有后台定时任务，也没有自动收取Issues的服务。

```sh
npm run kb:review
# 固定日期重放；JSON输出可由维护者显式重定向到自己的临时文件。
npm run kb:review -- --as-of 2026-09-13 --max-age-days 180 --json
```

默认as-of为执行当天UTC日期；重放日期必须不早于笔记核验和观测日期。命令复用kb:check的元数据与Markdown解析，在校验有效后输出候选、外链清单、观测索引和未比较的tested_with条目。导航不做年龄/运行时提醒；教学正文的未来日期、无效记录和缺失证据会退出1。正常候选退出0，需要人工判断。`kb:verify`已执行该命令，因此结构错误阻止部署，到期提醒不会让站点突然下线。

命令不访问网络、不写文件、不读取GitHub反馈。去重HTTP(S)外链保留笔记ID和位置；包括普通链接、引用式链接与外部图片，忽略代码块/行内代码。外链不天然等于权威来源。抓取成功、来源内容核对、可执行示例、UI验证必须分开记录。

运行时比较仅覆盖`.nvmrc`/`.node-version`、三个Python示例的`.python-version`与Java的`.java-version`。已识别的Node.js、Python/CPython、Microsoft OpenJDK版本不同会提醒；不查询上游最新版、不自动升级，不证明相同版本就兼容。Java比较三段或四段数字版本，构建号/供应商等仍需人工核对。库版本、OS和未识别写法列入`unCompared`，不能把零候选理解为完整依赖审计。

## 从信号到教材修正

1. **定位影响。** 记录文章稳定ID、位置、实际观察、当前版本与预期依据；先看已有BACKLOG，避免重复任务。私密材料留在仓库外，公开记录用最小脱敏输入。没有真实反馈就写“合成演练”，不编造用户或Issue编号。
2. **复现与分诊。** 在自建隔离副本运行最小例子，必要时核对对应版本官方文档正文。先写能够暴露错误的断言，再修例子和教材；解释问题用明确的读者任务逐句复核。如果未复现，保留命令、环境和差异，不标“已修复”。
3. **建立任务。** 需要后续工作的，在BACKLOG创建有依赖、验收条件和证据位置的任务；绑定已有任务也可以。到期候选每次根据源文件计算，不逐条复制为任务。已完成且无需改动的复查仍记录可读回执与实际结论，不能假造新代码问题。
4. **修正与验收。** 每批1–3篇，保留稳定ID和路径；处理先修、路线与交叉链接。执行受影响示例的成功/失败/边界和门禁。只有实际重新完成整篇适用内容/来源/示例复核才刷新`verified_on`；局部错字、提醒扫描、链接200、构建和部署都不足以刷新。`tested_with`只写实际执行环境。
5. **发布与反馈回执。** 报告区分本地修复、测试、同SHA部署。按当前自动普通push授权推送既有v5并核对Actions和HTTP；浏览器按集中计划另验。更新BACKLOG/STATE/执行计划，记录原反馈和修复证据关联。本地编辑回执不等于已发送回复；向他人发布评论仍需明确授权。

## 不同问题如何判断

| 信号 | 下一步与验收依据 |
| --- | --- |
| 180日到期 | 核对文章核心结论、官方来源和例子；保留无变化结论的证据，而非只修改日期。 |
| 固定版本变化 | 看版本范围、迁移说明及影响文章；用目标固定环境重跑成功/失败/边界，记录不兼容和兼容范围。不要批量替换tested_with。 |
| HTTP 200 | 阅读最终正文是否仍支持文章引用，排除软404/登录页；状态码只证明此次传输结果。 |
| 重定向、404/410 | 记录最终URL和官方替代页；核对语义后改链接。无替代依据时保留失败、建立修订任务。 |
| 403/429、超时或TLS失败 | 记录时间、方法、错误和有限重试结果；可用可访问的官方正文复核。不得写成200或绕过登录/访问控制。 |
| 用户无法复现 | 比较版本、路径、输入和失败步骤，用脱敏最小例子重现；未重现明确保留。 |
| 解释/先修不清 | 用反馈中的读者任务检查缺失概念和跳步，补例子与迁移练习，重新走该阅读路径。 |

当前check不支持已发布needs-update维护例外。确认错误需要撤下时设`status: needs-update`、`publish: false`，同时修订/撤下受影响的公开先修和链接，直至kb:check通过；不能只改一页让公开路径断裂。仅年龄或未判明403不触发这种变更。

## 观测索引和可读证据

[maintenance/observations.json](maintenance/observations.json)是当前文章关联的观测索引，无任务status字段；[回执模板](maintenance/REVIEW_TEMPLATE.md)列出所需证据。v1记录必填`id`、`kind`（external-link/version/feedback）、`observed_on`、`note_ids`、`summary`、`evidence`和`backlog_id`。evidence必须是仓库内非空reports/*.md；ID、重复项、日期、证据路径/符号链接和BACKLOG引用都检查。尚未分诊时显式`backlog_id: null`，命令生成候选；关联任务后的实际状态请读BACKLOG。

external-link另需`url`，且必须出现在所关联每篇文章的实际外链中；观测摘要说明访问与内容核验分别是什么结果。索引不是无限历史库：替换/移除来源或笔记时同步修订/移除该索引项，完整原观测和处理证据留在报告及Git历史。不要为了让检查通过改造历史事实。合法回执文件只证明证据位置存在，不能由机器证明报告真实。

JSON Schema历史记录引用H7-001实际403及正文核验报告，日期仍是当时日期。2026-09-14独立复查GET200及正文核验另存观测，见[首轮维护回执](../../reports/H7-m001-review.md)，不覆盖原记录。合成反馈演练只在测试临时目录，未登记为真实用户记录。

补丁兼容性使用[独立固定版本与操作说明](maintenance/runtimes/README.md)。该检查在自建副本中验证新补丁，不改历史复现版本或批量刷新文章日期；独立CI job也是发布前置门禁。

## 检查与恢复

`npm run kb:test`包含维护正反夹具；完整本地门禁见[VALIDATION](VALIDATION.md)。按报告保存命令、返回码、环境和NOT_RUN，失败守卫应能被独立故意破坏而检出。脚本只读性以运行前后字节对照验证，不靠口头约定。

交接从STATE引用的任务继续；重新核对实际Git根目录、工作区、HEAD和origin，保护用户修改。发布恢复沿用[RELEASE_RECOVERY](RELEASE_RECOVERY.md)，不因维护提醒自动回退线上或强推。

表单字段结构依据[GitHub官方issue forms语法](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)核对；本地检查配置与链接，未提交真实Issue或冒称浏览器表单已验收。
